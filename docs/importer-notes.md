# Rio importer behavior

`server/importers.ts` reads source buffers and never creates, edits, moves, or deletes source/inbox files. The test fixtures are temporary synthetic files, including real XLSX archives generated with ExcelJS; they never populate the application database. The actual Rio paths were absent on this Mac, so real-file integration remains unverified.

## Paths and reports

`importRio({home, paths, now})` defaults to the OS home directory. `home` replaces that directory; `paths` may override `applications`, `opportunities` (Markdown ledger), `workbook`, `linkedin`, `dental`, `social`, and `memory`. Leading `~/` expands against the chosen home. `social` defaults to `workspace/content-crew/deliveries/*/PLAN.md`; `memory` defaults to `memory/????-??-??.md`. Wildcards match a single path segment; recursive `**` and shell expansion are unsupported. Wildcard discovery skips symbolic links. Source reports retain each requested path or pattern even when absent. One pattern report aggregates its matching files, while records retain each actual file path.

Reports distinguish missing paths from read/parse errors. `records` counts accepted records; `skipped` counts malformed/unrecognized activity rows and ignored table totals; `message` carries line/worksheet diagnostics and invalid-date warnings. An accessible empty/unrecognized source remains `ok` with an explicit no-recognized-records warning. One missing or corrupt source does not prevent other sources importing.

## Formats and uncertainty

Markdown imports recognize conventional pipe tables (including escaped pipes), flexible heading aliases, date headings, explicit date-only lines, labelled activity bullets, and common explicit sent/planned LinkedIn and application activities. Tables require a separator row. Company/role/person/platform/stage/status/date/output/waiting fields have common aliases. Ambiguous free prose stays in the source and unrecognized bullets produce diagnostics. Fenced code blocks are ignored. This is conservative structured ingestion, not natural-language extraction.

ISO calendar dates and English named-month dates with a year are accepted after calendar validation. Slash dates such as `03/04/2026` are ambiguous and stay null. Missing dates stay null; no source mtime or import date becomes an activity date. Date headings apply to subsequent rows. Explicit invalid row dates stay null instead of falling back to their heading. Daily memory is one summary record per file. Aggregate bullets remain summary records; table totals never become individual contacts or posts.

Application executions use explicit applied/event dates (or their dated section), never an `Updated` column. Applied-date aliases are preserved separately as `metadata.appliedAt`; update dates are `metadata.updatedAt`. Snapshots may use the explicit update date as their snapshot timestamp for state ordering, without implying an application was executed that day. A blank applied date and populated update date produce an unknown application execution timestamp. The source excerpt retains both original date cells.

Opportunity ledger/workbook rows, dental leads, and social posts are snapshots. Application/LinkedIn activities are execution records. The action/status text must support completion; planned, pending, negative, and unknown states are preserved. A LinkedIn application channel alone does not imply outreach. Social counts require individual per-platform records; aggregate prose cannot manufacture posts. XLSX values are read with ExcelJS, including cached formula results and rich text/hyperlinks. Formulas are never evaluated; uncached formula values stay empty. The first recognized company/person header in each worksheet supplies the schema.

Negative completion phrases (`not submitted`, `not accepted`, `not replied`, `not received`, `not completed`), common contractions/auxiliaries, and `unsent`/`incomplete` forms are pending, not success. `Not successful`/`unsuccessful` means failed. Negated blocked/failure phrases do not themselves establish those states; positive controls such as `not blocked; submitted` and `not only submitted but accepted` preserve the actual positive claim. This finite phrase parser cannot reliably interpret arbitrary natural-language scope; ambiguous records should be reviewed against their original excerpts.

## Identity and provenance

Record IDs are deterministic from agent, path, source location, action, target, and exact detail. Reimporting unchanged content returns the same IDs. Moving/reordering source rows or changing their text can produce new IDs, so consumers must use semantic entity/event deduplication as well. Application/interview/assessment snapshots share `application:<company>:<role>` entity keys; contacts use person identity, dental uses practice/person identity, and social uses platform/title identity. Normalization ignores punctuation/case. This can merge genuine same-name entities and cannot infer whether differently spelled names mean the same entity.

LinkedIn `metadata.touchType` distinguishes message/connection/inmail/reply when evidenced. Explicit `Event ID` columns become `metadata.eventId`. Multiple same-type touches for the same person on the same day without explicit IDs are inherently ambiguous across overlapping sources; no event identifiers are invented to defeat deduplication. Every record retains its original Markdown line/excerpt or worksheet/row/excerpt.

`importInbox(directory, now)` accepts `.json` objects, arrays, `{records:[...]}` documents, and newline-delimited `.jsonl`. It validates rows independently and rejects unknown action/status/kind, missing agent/target, invalid timestamps, nested/nonfinite metadata, and malformed JSON. Dates must be strict ISO date-only or timestamps with seconds and a timezone; no textual/slash dates in the common inbox schema. Optional ID/entityKey/recordKind/metadata are supported. Explicit IDs are hashed with agent identity and preserved in `metadata.externalId`. Supplied provenance is ignored in favor of the actual inbox file and line. JSON object locations retain actual source lines even in formatted arrays. Invalid primitive/array entries are rejected with a document-level line fallback. Subdirectories/symlinks and non-JSON files are ignored. Empty inbox directories are reported without writing them.

Inbox supports the dashboard action types plus `output`, retaining `metadata.runId`, embedded `metadata.content`, and explicit artifact links for backend output verification. Explicit ID hashing matches API normalization, so an agent's same explicit ID is idempotent across both channels. Without an explicit ID, source-derived importer IDs differ from API content-derived IDs. The inbox's finite action list is deliberately narrower than the API's extensible identifier syntax; it permits missing timestamp (null) and missing detail (empty string), while the API requires those fields explicitly. Use explicit common-schema fields and IDs for interchangeable producers.
